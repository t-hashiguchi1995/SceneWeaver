1. 正本とリリース固定

R1はGitHub mainを基準とする歴史的設計書として保持する。R2の基準はこのワークスペースのコードと記録。今回GitHubの最新mainは再取得していないため、リモートとの一致は未確認。

確認したローカルブランチ：main
基底HEAD：633ce6e2899ffe547e1100fb2302cf996199af69
R2編集前の変更・未追跡エントリ：124件（ディレクトリは1件として数える）

基底HEADは検証済みコードのSHAではない。既存の検証結果には未コミット変更が含まれ、コードと検証の対応はまだ固定されていない。v0.2.0-rc1は候補名であり、現時点で作成済みとは扱わない。

  1. 変更一覧をレビューし、コード・テスト・設計書を候補コードコミットCへ固定。秘密情報、ブラウザプロファイル、runtime DB、認証情報を含めない。検証用画像を追跡するかは方針と容量を確認する。
  2. Cのクリーンなcheckoutで full Backend、Frontend build、mock browser、real Comfyを実行。外部投稿smokeは専用の明示的テストとして実行し、一般の回帰試験では公開しない。
  3. 検証記録に validated_code_sha=C、tracked treeのclean/dirty、実行コマンド、日時、環境、件数、skip、失敗、外部投稿URLを記録。未設定の実LLMはpendingとする。
  4. 結果文書を別コミットDへ追加。Dが文書だけの差分であることを確認してrcタグを付ける。タグDと検証コードCの関係を明記する。C以後のコード変更には影響範囲の再検証が必要。
  5. マイグレーション、バックアップ・復元、構成変更時の再生成停止をリリース判断に含める。既存の小規模成功だけで安定運用の合格とはしない。

4. Publish統合のDomainと責務

Master Release→Edition Preview→承認済みSnapshot→Publication Job→PublishingPort→Platform Adapter→専用Chrome

現行スクリプトの直接呼び出しをアプリの公開機能にしない。各サービスのUI操作経験をAdapterへ移し、認証接続・公開状態・復旧・画像準備はApplicationとDomainで扱う。

  platform_overrides = { x, pixiv, patreon }

Master + Platform Overridesを正本にする。生成済みの各サービス文字列はPreviewと承認Snapshotに固定し、後日の変更で送信内容が変わらないようにする。assetsはUUID参照・順序・ハッシュを持ち、cropは生成済みvariant Assetへ解決する。承認後の編集は新revisionと再承認を必要とする。

Domain

承認、状態遷移、画像順、再送可否、結果不明の解決。外部ブラウザ依存を持たない。

Application・Worker

Snapshot固定、Job作成、lease、Asset解決、事前検証、結果保存・再確認。

Adapters

UIから入力・添付・送信し、投稿ID・URL・確認証拠を返す。CookieやpasswordをAPIへ返さない。

6. 状態・失敗・再試行

draft → approved → queued → publishing
                              ├ succeeded（投稿ID/URL + 確認）
                              ├ failed（未送信と確定できる失敗）
                              └ ambiguous（送信後に結果不明）

ambiguous → succeeded       投稿済みを確認し証拠を記録
ambiguous → queued          未投稿の根拠 + ユーザーの明示的再試行
failed    → queued          原因解消・同一Snapshotの明示的再試行
queued    → cancelled       未送信のみ（監査履歴を残す）
障害分類復旧
画像不足・ルール違反・ログイン切れ。送信開始前。failed / auth_required原因・必要な操作を提示。認証はユーザーが専用Chromeで実施。
公開ボタン後のtimeout・接続断・レスポンス解析失敗。ambiguous自動Retry禁止。公開先確認、URL・ID・日時・assetに基づいて照合。
Worker再起動・lease期限切れ。送信開始markerあり。ambiguous別Workerは送信を引き継がず結果確認のみ。markerはクリック前に永続化。
Worker再起動。markerなし、未送信と確定。queuedlease更新と事前検証後に再開。並行workerの送信開始をDBで直列化。
画像upload完了、本文未送信。未公開のdraft残存外部draftを記録・再利用または明示的破棄。新しいdraftを重複作成しない。
3サービスのうち一部成功。platform別に保存成功済みは再送しない。残りの失敗・結果不明のみ対応。

結果不明の復旧デモ

ambiguous：公開ボタン後に接続が切れました。

設計例のみ。どのボタンも外部へ送信しない。本番では根拠・URL・確認者・時刻を監査記録へ保存する。

認証・接続の条件

ユーザーが専用Chromeでログインし、パスワード保存・同期を使わない。接続確認はログイン完了後に行い、認証情報を取得・exportしない。接続先はloopback上の専用browserのみ、操作対象のdomainをallowlistで制限する。接続endpointは認証権限を持つ秘密相当としてログに記録しない。

遠隔CDPの誤接続・他のタブへの操作を防ぐpairingと接続失効を設計する。シークレットセッションは閉じると失効するため、予約時刻までの認証保持を前提にしない。auth_requiredをUIへ返す。ログ・trace・スクリーンショットはフォームの秘密情報を避け、機密データを保存しない。

7. 実LLM・画像の品質評価

実LLM：10〜30の固定シナリオ

Persona／一人称・呼称／Continuity／Intent／Naturalness／Redundancy／Length／Locked-state safetyを項目ごとに評価。キャラクター設定・確定セリフ・前コマ状態をfixtureに固定する。

モデル名・provider・prompt version・入力hash・生成設定・候補を保存。合否閾値は人手の基準作成後に決定し、LLM自身のCritic点だけで合格にしない。stubでの反復は実モデルの品質測定から除外。

画像Review：Reject理由

顔・Identity／衣装／手・人体／Pose／構図／背景／Prompt不一致／その他。複数選択＋補足を記録する。

AssetDecisionは採否、QualityReviewは観察と理由を保持。採用時も欠点を記録できる。画像hash・Attempt・Profile・モデル・seed・評価者・日時を関連付ける。

QualityReview
  asset_id, generation_attempt_id, rubric_version
  dimension_scores[], reject_reasons[], notes
  evaluator_id, evaluated_at, context_snapshot_hash

評価UIはGeneration Reviewへ追加し、4候補の並列比較を維持する。手指などの欠点をUIに表示する一方、モデル別集計は十分な件数・同じ入力条件・評価基準のversionが揃ってから解釈する。生成成功と品質合格を別の指標にする。

8. CSP・ModelModifier・Content Rating

CSP：手動Round-tripから

HandoffRevision r005 → CLIP STUDIOで仕上げ → 画像Export
  →「仕上げ結果を取り込む」→ ExportRevision e001
  → Source Handoff r005 + page順 + hashを保存 → Release assets

最初は画像ファイルの明示的選択とpage mapping。パス・MIME・decode・page番号・重複・ファイルhashを検証し、入力をAsset Storeへコピーする。元Handoffを上書きせず、e001に対応revisionと元ファイル名を保存する。ページ欠落・順序不明・重複は確認してから確定。watcherは手動取込が安定してから。

LoRA：ADR 0011を拡張

Prompt Component → BuiltPrompt.model_modifiers
  { kind: lora, registry_id, version/hash,
    strength_model, strength_clip }
  → Registry解決 → WorkflowのLoader slot

positive / negative → Text Encoder（modifier文字列を渡さない）

任意パスや任意ファイル名は受け付けず、承認済みRegistryから選択。Workflow・モデル・CLIPとの互換性、強度範囲、複数LoRAの順序を明示し、hashと順序をAttemptに固定。未対応slot・不明モデルは生成前停止。旧単一strengthの変換はversion付きルールとして定義。

Content Rating：区分の伝播を検証

projectの保存だけではprofileの有効区分にならない。Project／Profile／Componentの区分を有効contextに含め、低い区分のProfileで高い区分のComponentが通らないことをImporterとruntimeの両方で検証する。区分不明は許可せず警告またはエラーとする。

区分付きの非性的ダミー素材
  → Importer → Library → 明示Profile
  → Draft → fake Generation → Review → immutable snapshot

general profile → adult区分のmarker・modifierが混入しない
adult profile   → 許可した区分のmarkerを明示選択できる
profileの変更 → stale判定・再構築・過去履歴保持

この区分E2Eは非性的fixtureで行う。成人向け区分機能の実装・検証と、露骨な性的画像の生成・評価は別。実モデルの画像品質を区分ラベルだけで検証済みにしない。

10. 根拠と適用範囲

  • R1（歴史的設計書）、ローカルUI実装説明
  • Sidebar・App Shellコード、Project Dashboard画面、Dashboard集計
  • 実Comfy・素材取込の検証、品質比較・stubの限界、カフェ4コマ

  • ADR 0011：Assembly / ModelModifier

新規API・Domain・wireframe・Sprintは設計案。現行コードへ実装済みとは扱わない。通常回帰では外部投稿をmockし、実投稿は対象・内容・公開範囲が明確に許可された専用検証でのみ行う。今回のユーザー許可を、将来の任意作品の公開許可へ拡張しない。
